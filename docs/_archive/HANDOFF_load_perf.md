## Замер, от которого пляшут карточки

Прод `athlete-pro-v7.vercel.app`, версия 1.27.1. Снесены SW + Cache Storage + IndexedDB + localStorage → холодный заход → тёплый. Байты по проводу — `curl` с `Accept-Encoding: br, gzip` по всем 126 файлам прекеша. Метрики — `npm run lhci` (mobile, 4G + CPU×4).

**Как повторить замер** (пригодится, чтобы доказать эффект карточки, а не поверить на слово):

```bash
npm run lhci   # ТОЛЬКО из worktree — корневой чекаут даёт фейковые цифры
```

Байты прекеша по проводу:

```bash
node -e "const fs=require('fs');const sw=fs.readFileSync('sw.js','utf8');const l=sw.match(/const ASSETS = \[([\s\S]*?)\];/)[1].split('\n').map(s=>s.trim().replace(/^'|',?$/g,'')).filter(s=>s.startsWith('/'));fs.writeFileSync('assets.txt',l.join('\n'))"
while read -r p; do curl -s -o /dev/null -H 'Accept-Encoding: br, gzip' -w "%{size_download} $p\n" "https://athlete-pro-v7.vercel.app$p"; done < assets.txt | awk '{s+=$1} END {printf "%.0f KB\n", s/1024}'
```

### Второй заход

**Ноль байт по сети** — всё, включая `index.html`, отдаёт SW. Фонового трафика в простое нет.

Но DomContentLoaded падает лишь на 11% (3651 → 3243 мс в замерочной панели). **Это главный вывод аудита: узкое место не сеть, а глубина цепочки модулей и работа стилей.** Сеть после первого захода бесплатна, а старт почти такой же.

Цепочка на прогретом кеше — **12 волн**, каждая ждёт предыдущую:


Ленивая загрузка JS **работает как надо** и трогать её незачем: Stats добирает 3 модуля, Train 10, Profile 11, вперёд по экранам ничего не тянется.

## LOAD-1 · Ленивый CSS по образцу ленивого JS — ВЗЯТА (1.27.2)

- **ЦЕЛЬ:** грузить стили экрана вместе с его модулем, а не все 13 файлов в `<head>`.
- **ФАКТ ИЗ КОДА:** в `index.html` все 13 `<link rel=stylesheet>` стоят в шапке и блокируют рендер, включая экраны, которые за сессию можно не открыть: `analytics` · `journal` · `privacy` · `athlete-room` · `body-stats` · `intel` · `claude` · `summary`. При этом JS этих же экранов уже ленивый — асимметрия чистая, механика для копирования есть рядом.
- **Чем подтверждено:** Lighthouse `unused-css-rules` — `base.css` на момент FCP использован на 18% (14 КБ из 17 мёртвым грузом). Style & Layout — 725 мс, крупнейшая статья главного потока после «прочего».
- **ЧТО ДЕЛАТЬ:** в шапке оставить `base.css` + стили первого экрана (`dashboard.css`); остальные подтягивать в той же точке, где лениво импортируется модуль экрана. Вставка `<link>` из JS перед первым рендером экрана, не `@import` (он сериализует загрузку).
- **ГДЕ СТОП:** только перенос точки загрузки. Содержимое CSS не трогать, селекторы не переписывать, `base.css` не дробить — дробление базы это отдельная карточка и отдельный риск.
- **НЕ ТРОГАТЬ:** ленивый JS (он уже правильный), `theme-boot.js` и порядок темы до первого кадра — вспышка тёмным вернётся мгновенно.
- **Мина:** экран, чей CSS приехал после разметки, моргнёт нестилизованным. Стили обязаны быть в DOM **до** первого показа экрана — грузить в `Nav.go` перед вставкой разметки и дожидаться `link.onload`.
- **DoD:** `npm run lhci` из worktree — FCP и Style & Layout ниже замера выше, performance не упал; переключение по всем вкладкам без вспышки нестилизованного; `npm test` зелёный.

### Как сделано и что из карточки оказалось не так

Реализация: `js/shared/lazy-css.js` (карта `SCREEN_CSS` + `ensureCss`), await в `Nav.go` **до** `startViewTransition` (внутри колбэка ждать поздно — снимок страницы уже снят), плюс две точки в `js/app.js` для Острова и Claude-FAB.

В шапке осталось четыре таблицы: `base.css` + `dashboard.css` (блокируют рендер, как и было) и `athlete-room.css` + `privacy.css` — они одевают статус-бар, который виден с первого кадра, и экранными не бывают. Девять остальных приезжают со своим экраном.

**Поправка к факту карточки:** «все 13 стоят в шапке и блокируют рендер» было верно лишь про две. Одиннадцать уже ехали с `media="print" data-lazy`, который `js/boot.js:10` переключает в `all` — то есть рендер они не блокировали, но качались и парсились на старте всегда. Выигрыш поэтому не в FCP, а в объёме каскада.

**Чем подтверждено (детерминированные числа, не прогон):**
- CSS-запросов до `load`: **13 → 4**;
- правил в каскаде на домашнем экране: **1337 → 757** (−43%);
- ~107 КБ CSS экранов вообще не участвуют в старте, ещё 40 КБ (Остров + Claude) уехали в idle.

**Чего доказать не вышло:** Lighthouse на localhost разницы не видит — по три прогона на ветку дали 94/95/99 до и 95/95/97 после, `styleLayout` 604–643 против 608–629. Это шум, а не эффект: симуляция 4G на localhost не оценивает то, что мы убрали. Честный замер эффекта — только на проде после выката (метод в шапке файла).

`npm test` 546/546 · `npx playwright test` 41/41 · все семь экранов проверены в браузере: свой CSS уже разобран в момент, когда экран получает `.active`.

## LOAD-2 · Плоская цепочка модулей через modulepreload — ВЗЯТА (1.27.3)

- **ЦЕЛЬ:** убрать ожидание слоями — 12 волн на прогретом кеше.
- **ФАКТ ИЗ КОДА:** сборщика в проекте нет и не будет (правило «vanilla only»), поэтому браузер узнаёт о модуле только разобрав того, кто его импортирует. Отсюда лестница: `theme-boot` → `boot`+`app` → `errors-ui` → 16 → 9 `db/*` → 8 `shared` → 10 → 2 → `cryptoClient` → `factory` → `onboarding`+`claude.view` → `block-ticks`.
- **ЧТО ДЕЛАТЬ:** в `index.html` добавить `<link rel="modulepreload">` на модули нижних уровней старта — браузер начнёт тянуть их сразу, а не открывая слой за слоем. Список брать из замера (волны с 5-й и глубже), не «на глазок».
- **ГДЕ СТОП:** только `index.html` и список. Ни один `import` не переписывать, порядок инициализации не менять — `modulepreload` меняет **когда скачано**, а не когда выполнено.
- **НЕ ТРОГАТЬ:** экранные модули (`analytics.*`, `journal.*`, `profile.*`, `workout.view*`) — они лениво и правильно.
- **Мина:** прелоад того, что грузится не всегда, превращает экономию в лишний трафик; в список идут только модули, которые стартуют **всегда**.
- **DoD:** число волн в замере уменьшилось (метод — в шапке файла), TTI по Lighthouse ниже, сетевой объём первого захода не вырос.

### Как сделано

Замер на локальном сервере (`node server.js`, 3 прогона тёплого кеша после сноса SW+Cache+IDB+localStorage) воспроизвёл ту же структуру волн, что и в шапке файла — это и стало точным списком, а не «на глазок». Волны 5–12 (34 модуля: 9 `db/*`, 8 `shared`, 10 `confirm/rest-timer/pip/…`, `workout-plans`+`chamber-pill`, `cryptoClient`, `ui/factory.js`, `onboarding.js`+`claude.view.js`, `block-ticks.js`) получили `<link rel="modulepreload">` в `index.html`, волны 1–4 не тронуты — они уже видны HTML-сканеру без подсказки.

**Чем подтверждено (детерминированно, не на глаз):** та же группировка resource-timing по разрывам старта на прогретом кеше даёт **12 → 3 волны** (`theme-boot` отдельно; всё остальное, включая `boot.js`/`app.js`, стартует одним фронтом). Запросов `.js` на экран **55, дублей 0** — прелоад задедуплицировался с последующим `import()` тем же URL, лишнего трафика нет. `npm test` 546/546, `npm run lint` 0 ошибок (18 предсуществующих warning не мои), все четыре вкладки таб-бара переключены в браузере — консоль чистая.

**Чего доказать не вышло:** `npm run lhci` из worktree зелёный (performance 99, TTI 3.3 s), но localhost не сравним с прод-замером 94/TTI 3.8 s из шапки файла — тот же урок, что в LOAD-1: локальная симуляция 4G не моделирует реальную сетевую задержку между волнами, которую и убирает `modulepreload`. Честный TTI-эффект — только на проде после выката (метод в шапке файла).

## LOAD-3 · Логотип в статус-баре: 34 КБ ради 32 пикселей — ВЗЯТА (1.27.4)

- **ФАКТ ИЗ КОДА:** `index.html:311` показывает `icons/icon-192.png` в `<img class="status-logo-img">`, а `.status-logo-img` (там же, `:157`) задаёт **32×32 CSS-px**. Файл — 192×192, 34 КБ. Вдобавок он же стоит в `<link rel="icon">`, и по трассе Lighthouse тянется **дважды**.
- **ЧТО ДЕЛАТЬ:** отдельный `icons/icon-64.png` (~3 КБ) под статус-бар; `<link rel=icon>` оставить на `favicon.ico` + 192-й.
- **ГДЕ СТОП:** только шапка приложения. Манифест и набор иконок установки не трогать — там 192 на своём месте.
- **DoD:** первый заход легче примерно на 65 КБ, логотип на 375px и при dpr 2–3 не мылит.

### Как сделано (одним заходом с LOAD-5, тот же `<img>`)

Инструмента для правки PNG в проекте не было (`sharp` поставлен временно, `--no-save`, в `package.json`/lock не попал). Из `icon-512.png` (единственного источника, векторного файла в репо нет) флуд-заливкой от углов вырезан фон — связная область, совпадающая с угловым `rgb(9,12,25)` в допуске, помечена прозрачной; бейдж (рамка со свечением + буква) остался закрашен, потому что отрезан от углов более ярким кольцом свечения и заливка до него не достаёт. Дальше `resize` до 64×64 (`lanczos3`) и палитровое PNG (`palette:true, colors:64`) — глазами разница на градиенте свечения не видна, а вес упал до **~0.8 КБ** (лучше карточной оценки ~3 КБ). `index.html:353` теперь ссылается на `icons/icon-64.png`; `<link rel=icon>`, `og:image`, манифест и `apple-touch-icon` не тронуты.

`scripts/build-sw.mjs` менять по сути не пришлось — `INSTALL_ICON_RE` фильтрует только `icon-384/512/maskable-512`, `icon-64` под него не попадает и сам лёг в прекеш (`npm run build:sw` → 128 файлов, `CACHE_NAME` автобамп). Комментарий в файле поправлен (там было «в UI живёт только icon-192» — теперь это не так).

**Чем подтверждено:** живой браузер (не только офлайн-композит) — `canvas.getImageData` на отрендеренном `<img>` даёт угловой пиксель `[0,0,0,0]` (альфа 0) и центр бейджа `[123,137,164,255]` (альфа 255, буква на месте) при `data-theme="light"`. `npm test` 546/546, `npm run lint` 0 ошибок (18 предсуществующих warning не мои).

## LOAD-4 · Иконки не сжаты: ~1 байт на пиксель — ВЗЯТА (1.27.5)

- **ФАКТ:** `icon-192` 34 КБ · `apple-touch-icon` 30 КБ · `icon-384` 134 КБ · `icon-512` 268 КБ · `icon-maskable-512` 162 КБ. Все 8-bit RGB без палитры. Для плоского логотипа норма 0.1–0.25 байт/пиксель, здесь 0.63–1.05 — то есть запас примерно четырёхкратный.
- **ЧТО ДЕЛАТЬ:** прогнать через квантование (pngquant/oxipng), глазами сверить градиент свечения — именно он мешает палитре, на нём и проявится потеря, если пережать.
- **ГДЕ СТОП:** только файлы в `icons/`. Разметку, манифест и `build-sw` не трогать.
- **Мина:** 512-е и maskable в прекеш не возвращать — они исключены осознанно (см. `INSTALL_ICON_RE` в `scripts/build-sw.mjs`), потолок прекеша 1.5 МБ.
- **DoD:** визуально не отличить в тёмной и светлой теме на телефоне; суммарный вес набора упал минимум вдвое.

### Как сделано

`pngquant`/`oxipng` в системе нет (тот же дефицит, что в LOAD-3) — квантование сделано `sharp` (`--no-save`, как и там), `png({ palette: true, colors: 256, effort: 10 })` на все пять файлов без альфы: `icon-192`, `apple-touch-icon`, `icon-384`, `icon-512`, `icon-maskable-512`. `icon-64` не тронут — он уже сжат в LOAD-3.

**256 цветов, не меньше:** проверено вживую на 512-м и 192-м — обрезка кадра со свечением, апскейл nearest-neighbour ×3. На 256 цветах пиксель в пиксель совпадает с оригиналом (в оригинале уже есть дизеринг-зерно, квантование легло внутрь него). На 128 — видимый ступенчатый контур на самом градиенте свечения, ровно та мина, о которой предупреждала карточка. Дальнейшее занижение до 64 давало тот же байт-вес, что и 128 (уникальных цветов в изображении уже ≤128), то есть выигрыша не несло, только риск.

**Вес:** 643 КБ → 277 КБ по пяти файлам (**−57%**, при требовании DoD «минимум вдвое»):

| Файл | До | После |
|---|---:|---:|
| icon-192 | 34 402 | 16 152 |
| apple-touch-icon | 30 720 | 14 882 |
| icon-384 | 137 688 | 58 867 |
| icon-512 | 274 715 | 116 716 |
| icon-maskable-512 | 165 794 | 70 427 |

Размеры, число каналов (3, без альфы) и формат — не изменились (проверено `sharp.metadata()` до/после). Прекеш не пострадал: `INSTALL_ICON_RE` по-прежнему исключает 384/512/maskable-512, `npm run build:sw` дал те же **128 файлов**, поменялся только `CACHE_NAME` (байты трёх precached иконок — `icon-192`, `apple-touch-icon` — изменились).

`npm test` 546/546, `npm run lint` 0 ошибок (те же 18 предсуществующих warning, не мои).

**Чего доказать не вышло:** «визуально не отличить на телефоне» из DoD — это глаз Gio в поле, не автоматика (тот же паттерн, что в LOAD-5). Здесь сделана пиксельная проверка на десктопном рендере (кроп + апскейл), не замена полевой.

## LOAD-5 · Логотип непрозрачный — на светлой теме тёмный квадрат — ВЗЯТА (1.27.4)

- **ФАКТ:** PNG без альфа-канала, угловой пиксель `rgb(10,13,26)`. На тёмной теме сливается с фоном статус-бара `rgb(5,5,7)` и выглядит бесшовно; на светлой фон `rgb(244,244,247)` — и в шапке висит тёмно-синий квадратик 32×32.
- **ЧТО ДЕЛАТЬ:** версия логотипа с прозрачным фоном под UI. Для установки на домашний экран непрозрачная как раз правильная — её оставить.
- **ГДЕ СТОП:** только иконка в шапке приложения; манифест и apple-touch не трогать.
- **DoD:** полевая проверка Gio в обеих темах — квадрата нет.
- **Связано:** сделано одним заходом с LOAD-3 (см. её раздел «Как сделано») — тот же `icons/icon-64.png` несёт и вес, и прозрачность.
- **Автоматической верификацией DoD не закрыть** — «квадрата нет» это глаз Gio на телефоне, не тест. Браузерная проверка (`getImageData` на живом `<img>`, см. LOAD-3) подтверждает, что альфа физически есть и что края прозрачные; окончательное «квадрата нет» — за полем.

## LOAD-7 · Шрифты: 46 КБ в прекеше под языки, которых в UI нет — ВЗЯТА (1.27.6)

- **ФАКТ:** 9 файлов, 125 КБ. Среди них `manrope-greek` (9 КБ), `manrope-vietnamese` (8 КБ), `manrope-latin-ext` (15 КБ), `manrope-cyrillic-ext` (2.5 КБ), `instrument-sans-latin-ext` (11 КБ). UI только RU/EN. Браузер сам их не качает — спасает `unicode-range` в `@font-face`, — но SW кладёт в кеш всё подряд.
- **ЧТО ДЕЛАТЬ:** исключить из прекеша заведомо неиспользуемые подмножества (по образцу `MEDIA_RE` / `INSTALL_ICON_RE`). Сами файлы из репо **не удалять** — `@font-face` на них ссылается, и при вставке греческого текста они должны догрузиться из сети.
- **Мина:** `latin-ext` трогать осторожнее прочих — это европейская диакритика, она может понадобиться в именах упражнений и в названии зала из шапки TXT.
- **DoD:** прекеш легче примерно на 30–45 КБ, кириллица и латиница в офлайне рисуются без подмены шрифта.

### Как сделано

`FONT_SUBSET_RE` в `scripts/build-sw.mjs` — тот же паттерн, что `MEDIA_RE`/`INSTALL_ICON_RE`: `/\/fonts\/(?:manrope-(?:greek|vietnamese|latin-ext|cyrillic-ext)|instrument-sans-latin-ext)\.woff2$/i`, все пять названных в карточке файлов, включая `latin-ext` из мины. Решение по мине: `sw.js` уже кеширует шрифты рантаймом (`cacheFirst`, тот же путь, что у медиа после F-7) — файл не в прекеше, но при первом реальном запросе (диакритика в имени упражнения/зала) браузер скачает и закешируется по факту использования, дальше офлайн работает как обычно. Это тот же компромисс, что уже принят для медиа и крупных иконок установки, поэтому `latin-ext` исключён вместе с остальными, а не оставлен «на всякий случай» — половинчатое решение здесь не DoD.

`npm run build:sw`: **128 → 122 файла** прекеша (types.d.ts + 5 шрифтовых подмножеств). Байты пяти шрифтов по диску — 45.7 КБ, что покрывает верх диапазона DoD (30–45 КБ; вместе с `types.d.ts` общий вес прекеша упал примерно на 56 КБ). Базовые `manrope-latin`, `manrope-cyrillic`, `instrument-sans-latin`, `orbitron-latin` остались в `ASSETS` — RU/EN рисуются из прекеша без обращения к сети.

## LOAD-8 · `/__build` даёт 404 при каждом открытии профиля — ВЗЯТА (1.27.6)

- **ФАКТ:** `js/profile.js` `_appendBuildStamp()` дёргает `/__build` — эндпоинт есть только у локального сервера, на проде его нет. Ошибка проглочена (`try/catch`), но каждый заход в профиль оставляет неуспешный запрос в сети и красную строку в консоли поля.
- **ЧТО ДЕЛАТЬ:** решить с Gio — либо звать только на localhost/LAN, либо не звать, если `VERSION` не dev-сборка.
- **ГДЕ СТОП:** одна функция. Штамп сборки на стендах должен продолжать работать — он куплен кейсом «ретест 0кг молча гонял старый worktree».
- **DoD:** в профиле на проде нет запроса к `/__build`; на стенде штамп по-прежнему появляется.

### Как сделано и почему такой вариант

Выбран первый из двух вариантов карточки — гейт по hostname, не по `VERSION`. `VERSION` одинаковый на стенде и на проде (тот же чекаут может служить оба), а `/__build` физически существует только у `scripts/telemetry-server.mjs` (localhost или `--lan`-адрес в приватной сети) — гейт по адресу сервера бьёт точно в причину, гейт по версии был бы косвенным и ломался бы в момент, когда кто-то тестирует прод-сборку локально.

`_isLocalHost()` в `js/profile.js`: `localhost` · `127.0.0.1` · приватные диапазоны `192.168.*`, `10.*`, `172.16–31.*` (диапазон, в котором `--lan` раздаёт адрес телефону). `_appendBuildStamp()` выходит до `fetch`, если хост не локальный — на проде (`athlete-pro-v7.vercel.app`) запрос к `/__build` теперь не происходит вообще, не «происходит и проглатывается».

**Проверено в браузере** (`scripts/telemetry-server.mjs`, localhost:3000): профиль показывает `ATHLETE PRO V1.27.6 · ELITE EDITION · CLAUDE/LOAD-TYPES-PRECACHE-F1D8B7@...`, запрос `GET /__build → 200 OK` в сети — стенд не сломан.
