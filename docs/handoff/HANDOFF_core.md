# HANDOFF — P.A.N.D.A. Core, перестройка ядра

> Заведён 2026-09-23 по итогам грилежа после аудита `CORE-1..3`. **Ждёт закрытия
> `LAUNCH-10`** — трек запуска (`docs/handoff/HANDOFF_launch_track.md`) не блокирует,
> но и не начинается раньше него. `CORE-1`/`CORE-2` (безопасность/лимитер) и `CORE-S`
> (пачка перед раздачей: стрим, флаг фото, ромб FAB, self-host supabase, плашка airgap)
> — там же, отдельная линия.
>
> Порядок карточек фиксирован решением Gio 23.09, не переставлять без разбора:
> **`CORE-4` (снимок) → `CORE-5` (один клиент) → `CORE-6` (UI из снимка) / `CORE-8`
> (airgap) → `CORE-7` (промпт) → `CORE-9` (качество)**. `CORE-6` и `CORE-8` — пара:
> обе читают один и тот же снимок движков, вести можно в любом порядке внутри пары,
> но обе — после `CORE-5` и до `CORE-7`.

## Почему в этом порядке

Каждая следующая карточка стоит на артефакте предыдущей: `CORE-6` красит снимок,
которого нет без `CORE-4`; `CORE-7` режет промпт, который сперва должен стать снимком,
а не сырыми записями; `CORE-9` меряет качество ответов, которые к этому моменту уже
идут по новому контракту. Сборка в обратном порядке — тот же класс дефекта, что
отвергнутая линия «phase 8» (`docs/_archive/HANDOFF_intel_readiness.md`): второй путь
данных мимо уже работающего.
