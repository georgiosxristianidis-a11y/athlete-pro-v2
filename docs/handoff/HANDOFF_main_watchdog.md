## Где сейчас правда

**Сторож на `main` мёртв.** Поставлен в 1.27.23, за всё время отработал один раз и упал:
единственный прогон — `failure` со `Unhandled error: HttpError: Resource not accessible by
integration`. `permissions:` не содержал `pull-requests: read`, а `github-script` зовёт
`GET /repos/{owner}/{repo}/commits/{sha}/pulls`. Всё, что не перечислено в явном блоке
`permissions:`, получает `none` — отсюда 403.

Убивает не один сигнал, а оба: необработанная ошибка валит job целиком, вместе с проверкой
зелёности CI, которая идёт **до** запроса PR. То есть дыра, ради которой сторож делался,
всё это время стояла открытой и выглядела закрытой.

**Фикс готов, но НЕ влит** — ветка `claude/watchdog-alive`. PR был открыт и закрыт (см.
«Аномалии»). Проверять состояние ancestry, а не эту строку:

```bash
git fetch origin && git log origin/main --oneline -- .github/workflows/main-watchdog.yml
```

## Что в ветке

- `pull-requests: read` (связанные PR) + `actions: read` (прогон CI по `run_id`).
- Каждый вызов API обёрнут. 403/404 на `/pulls` деградирует в issue «сторож не смог
  проверить происхождение коммита» с отдельным заголовком — ослепший сторож не обвинитель.
  Отказ дедупа → предупреждение и issue всё равно. Отказ `getCommit` → тело issue со
  ссылкой, собранной из SHA. Падаем намеренно ровно в одном месте: не вышло завести issue,
  там сигналу больше некуда деться.
- Дедуп переехал с `search.issuesAndPullRequests` на `issues.listForRepo`: поисковый индекс
  отстаёт на минуты, на быстрой серии коммитов сторож завёл бы второй issue на тот же SHA.
- `workflow_dispatch` с входом `run_id` — единственный способ проверить сторожа, не пушнув
  в `main` напрямую.
- Baseline воспроизведён на моках Octokit, 14 сценариев: старый скрипт на 403/404 падает
  тем же `HttpError`, новый — заводит issue и живёт.

## Карточка WATCH-1 — закрыть живой проверкой

Гейт на ветке зелёный, но **пункт «проверено» не закрыт**: 2026-08-06 GitHub Actions ушли
в major outage (15:22 UTC), прогонов не было. Без лога прогона карточка открыта.

Порядок обязателен: `workflow_run` берёт файл воркфлоу с **дефолтной** ветки, значит
исправленный сторож не запустится, пока не влит в `main`.

1. Перетриггерить чеки на ветке — события пушей, сделанных в окно аварии, GitHub теряет
   насовсем, само не соберётся.
2. Зелёный CI → `gh pr merge --rebase`.
3. Прогон сторожа на мёрж-коммите обязан быть **зелёным** и написать
   `main <short>: CI зелёный, PR #… — чисто.`
4. Ручной прогон на заведомом нарушении — обязан **реально завести issue** с находкой
   «нет связанного смёрженного PR»:

```bash
gh workflow run main-watchdog.yml --ref main -f run_id=29770664500
```

`run_id=29770664500` — прогон CI на коммите `4ad7117` (20 июля): CI зелёный, но связанного
смёрженного PR нет, то есть прямой пуш мимо хука. Найден перебором ~180 прогонов CI на
`main`; на всех прогонах позже 27 июля нарушений нет, так что заменить его на свежий
не выйдет.

## Карточка WATCH-2 — слепое пятно: CI не запускался ВООБЩЕ

Найдено 2026-08-06 на живом инциденте, в текущем фиксе не закрыто.

Сторож висит на `workflow_run` от CI. Если CI на коммите не запускался вовсе — события нет,
сторож не просыпается, и коммит въезжает в `main` абсолютно молча. Ровно это и произошло:
в окно аварии два PR слиты в `main` с **нулём check-runs** (`gh api
repos/:owner/:repo/commits/<sha>/check-runs` → `total_count: 0`).

Хуже того, `combined status` на этих коммитах — `success`, потому что единственный контекст
там от Vercel. **Зелёная галочка в UI ≠ чеки прошли**: считать `check-runs`, а не смотреть
на цвет.

Что нужно: второй вход, не зависящий от того, добежал ли CI. Например `schedule` (раз в
час) или `push` на `main`, шаг «у HEAD `main` есть хоть один завершённый check-run от CI» →
иначе issue. Держать в том же файле и тем же принципом «не падать»: отказ API — жалоба,
а не красный прогон.
