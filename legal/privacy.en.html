Privacy Policy

This page describes what Athlete Pro actually does with data, checked against the application code rather than a generic template. The publisher confirms whether the wording is legally fit. Contact: georgiosxristianidis@gmail.com.

1. Who processes data

The controller is the publisher of Athlete Pro. The service is an installable PWA at athlete-pro-v7.vercel.app. Pages and the API are hosted on Vercel. This draft does not name a separate legal entity: for data requests, use the address above.

2. What stays on the device

The training log lives on your device. The IndexedDB database is named athlete-pro, schema version 4. There are seven object stores:

  • workouts — completed sessions: type (push / pull / legs), date, duration, tonnage, exercises and sets (weight, reps, RPE, whether the set was done).
  • oneRM — estimated one-rep max per exercise (Epley formula).
  • bodyMetrics — weight, height, BMI. On HTTPS the record is encrypted on-device (AES-256-GCM; the key lives in a separate database ap-keys and is not extractable). On plain HTTP (for example a LAN URL) there is no encryption: values are stored as base64 and are not sent to the cloud.
  • events — a local application event log. It is not synced to the cloud.
  • settings — key–value preferences: language (lang), profile (name, date of birth, sex, goal, experience, equipment, limitations, resting heart rate), privacy mode, the AI-coach toggle, the usage-counter queue, BYOK keys.
  • nutritionLogs — meal entries, if you log them.
  • plannedWorkouts — plans, including ones generated by the AI.

The same origin also keeps service keys in localStorage: install id (ap-device-id), the sync queue, the pull cursor, flag overrides, usage self-exclusion, seven-day recommendations, and the Dynamic Island layout profile. Coach chat history lives in the tab’s memory and is gone on reload.

3. Three privacy modes and the AI toggle

A new install defaults to airgap: sync and AI are blocked, and the AI toggle is off. If the device already had workouts when this system appeared, the mode stays cloud with AI on — matching previous behaviour.

  • Air-gapped. Nothing is queued for the cloud. AI requests are blocked. The AI toggle cannot be turned on in this mode: the app answers with local rules over your own data.
  • Anonymous. AI can be enabled. The safeFetch wrapper strips Authorization, X-User-Id, X-Device-Id and Cookie headers, and top-level JSON fields userId, deviceId, email, name. Cloud sync uses the Supabase client, not that wrapper: when cloud is configured, records are still written under the anonymous Supabase session id.
  • Cloud. The AI coach (if the toggle is on) and sync (if cloud is configured) are available.

The last 50 network attempts are stored in the privacy.audit setting (path only, query string stripped). That log stays on the device and is not synced.

4. What leaves the device

Only the paths that exist in the code. If a path is off, nothing is sent on it.

4.1. Cloud replica (Supabase)

If the build has a Supabase URL and anon key, and the mode is not airgap, the client may create an anonymous session and refresh it every ten minutes. Six stores go to the server: workouts, 1RM, body metrics, settings, nutrition, plans. The events store is not synced. Settings keys that start with ap-*, the audit log, and anything whose name ends in key / token / secret / password (including Anthropic and Gemini BYOK keys) never enter the sync queue.

When cloud is configured in the build, the Supabase client library is loaded from jsDelivr. That is a script download, not an upload of training data.

4.2. AI coach (Anthropic Claude or Google Gemini)

The AI toggle is off by default on a new install. When it is on and the mode is not airgap, the browser posts POST /api/coach to our server (10 requests per minute). The server proxies the request to the selected engine. The body is a compressed context, not the raw database:

  • up to five recent workouts: type, hours ago, tonnage, duration, exercise names and completed-set counts;
  • muscle-fatigue scores and up to five top 1RMs;
  • from the profile: name, age (derived from date of birth), sex, goal;
  • the chat text (up to 40 messages, each up to 12,000 characters).

A separate recommendations call (/api/coach/recommendations) may send weights, reps and RPE from the last session and the next-session plan. A BYOK API key is sent to our server as customKey and then to the selected engine; it is not written into the cloud settings replica. The server strips secret-shaped keys from the prompt snapshot again if a caller forgot.

Server logs redact weight, height, bmi, password, token, authorization and cookie. That is not a claim that the model prompt omits training context: the prompt does include the workout context listed above.

4.3. Usage counter (Vercel Web Analytics)

The counter sits behind the usage-stats flag, which is off by default: the script is not loaded and no events are sent. If the flag is ever turned on, only three event names leave the device: app_open (app version and privacy mode), workout_completed (workout type), coach_message (empty payload — the fact of a question, not the text). In airgap the payload is stripped entirely. Never sent: coach message text, exercise names, weights, tonnage, device id, keys.

Even with the flag on, the counter stays silent if the browser sends Do Not Track or Global Privacy Control, if the device is self-excluded, if the Privacy toggle is off, or if this is not a Vercel production host. The offline queue holds at most 50 entries for 7 days, in the ap-usage-queue setting, and is not synced.

4.4. Hosting

Any page view, including this document, is an ordinary HTTPS request to Vercel (IP, URL, User-Agent). The legal pages themselves do not load an analytics script.

5. Why we process this

  • The local log and settings exist so the app works without a network.
  • The cloud replica exists to merge devices, and only when you are not in airgap.
  • Coach context exists so the answer can use your sets instead of an empty chat.
  • The three counters exist so the publisher can see whether the product is alive.

6. Access, export, deletion

In the app: Profile → Privacy → data passport (per-store counts) and privacy budget (recent network attempts). The JSON export contains workouts, 1RMs, metrics and settings — not the event log, nutrition, or plans.

“Delete all data” clears five local stores — workouts, 1RM, metrics, events and settings — then reloads. Nutrition, plans, and the ap-keys database are not touched by that button. Clearing the site’s data in the browser removes all seven stores, ap-keys, and localStorage.

A local wipe does not delete an already-uploaded cloud replica: the app has no “erase my server account” command. To delete cloud rows, write to the address at the top of this page.

7. Children

The service is not directed at anyone under 16. Date of birth in the profile exists so the AI coach can receive an age, not as an age gate at sign-in. If you believe a child’s data is in the service, write to us — we will delete what we can on our side.

8. Retention

On the device — until you delete records or site data. In the cloud — for as long as the anonymous session and table rows exist; the code has no timed auto-delete. The usage queue expires after 7 days. Recommendations in localStorage expire after 7 days.

9. Recipients

The publisher does not sell training data. Along the paths above, data may be seen by: Vercel (hosting and, if the flag is on, Web Analytics), Supabase (cloud replica), Anthropic and/or Google (AI coach), jsDelivr (the Supabase client file). Their own terms apply on their infrastructure.
