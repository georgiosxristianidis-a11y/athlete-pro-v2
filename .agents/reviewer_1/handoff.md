## 2. Logic Chain

1. **Client Clock Advancement Failure**:
   - In HLC architecture, when a node receives a remote timestamp $T_{\text{remote}} = (l_r, c_r, \text{node}_r)$, it MUST advance its local clock state via `hlcReceive` so that future local writes generated by `hlcNow` receive physical component $l \ge l_r$.
   - In `js/sync.js`, when `runSync()` pulls records from the backend, it writes them into IndexedDB via `DB._putRaw` without calling `DB.hlcReceive(remoteRecord.hlc, DB.getDeviceId())`.
   - If Client B receives a record written by Client A (whose clock was skewed +10 minutes), Client B's internal HLC state (`stateL`) remains at real physical time.
   - When Client B subsequently writes a new local record via `withMeta`, `hlcNow` generates a timestamp with physical time $l \approx \text{real time}$, which is 10 minutes BEHIND Client A's skewed timestamp.
   - When Client B pushes its new record to the server, the server calls `lwwWins(R_B, R_A)` and compares HLC timestamps. Since $l_B < l_A$, the server discards Client B's write as an older record.
   - Therefore, Clock Skew Data Loss occurs on subsequent client writes.

2. **Self-Certifying Test Bypass (Integrity Violation)**:
   - In `test/hlc-and-sync-security.test.js` lines 86–90, the test for "Clock Skew Data Loss Resolution scenario" explicitly calls `hlcReceive(recordA.hlc, 'device-b-normal')` inside the test script.
   - Because `hlcReceive` was called in the test script but never integrated into `js/sync.js`, the test suite passed (36/36) while the actual client sync engine in `js/sync.js` remained broken.

3. **Inconsistent LWW Comparison in `js/sync.js`**:
   - In `js/sync.js` line 151, the decision to overwrite `localRecord` relies on `remoteRecord.updatedAt > localRecord.updatedAt`.
   - This bypasses HLC counter `c` and `node` tie-breaking, causing non-deterministic split-brain state when two records have equal `updatedAt` values.
   - It also fails fallback handling for legacy records handled by `lwwWins`.

## 4. Conclusion

Verdict: **`REQUEST_CHANGES`**

### Finding 1 [Critical — Tagged: INTEGRITY VIOLATION / INCOMPLETE INTEGRATION]
- **What**: Client Sync Engine (`js/sync.js`) fails to call `hlcReceive` and `lwwWins` during sync pull, breaking HLC causality and causing Clock Skew Data Loss on subsequent writes. The unit test in `test/hlc-and-sync-security.test.js` masked this bug by manually invoking `hlcReceive` inside the test file.
- **Where**: `js/sync.js` (lines 119, 144–157) and `test/hlc-and-sync-security.test.js` (lines 86–90).
- **Why**:
  1. Without `hlcReceive` during pull in `js/sync.js`, receiving remote records with skewed timestamps does not advance the local HLC clock. Subsequent client writes generate lower HLC timestamps and are rejected by LWW merge upstream.
  2. `remoteRecord.updatedAt > localRecord.updatedAt` bypasses `lwwWins` tie-breaking and HLC comparison.
  3. `records.filter(r => r.updatedAt > lastSync)` in push phase does not handle HLC timestamps without an `updatedAt` field.
- **Suggestion**:
  1. In `js/sync.js`, import `lwwWins` from `./shared/lww.js`.
  2. Update push payload filter to `(r.hlc?.l ?? r.updatedAt ?? r.timestamp ?? 0) > lastSync`.
  3. In `js/sync.js` pull loop, for each record in `pullData.changes`:
     ```javascript
     if (remoteRecord.hlc) {
       DB.hlcReceive(remoteRecord.hlc, DB.getDeviceId());
     }
     if (!localRecord || lwwWins(remoteRecord, localRecord)) {
       await DB._putRaw(store, remoteRecord);
       pulledCount++;
     }
     ```
  4. Update `test/hlc-and-sync-security.test.js` (or add a test in `test/sync-resilience.test.js`) to assert that calling `runSync()` with a pulled skewed remote record actually advances `hlcNow()` on the client.
